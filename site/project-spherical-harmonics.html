Spherical Harmonics

C++ · raylib · WebAssembly Project 15

Spherical harmonics are how real-time renderers store an entire environment's lighting in a handful of numbers. This one takes a 1k HDR environment map, projects it down to at most 16 coefficients per colour channel, and reconstructs it again so you can see exactly how much of the original survives. The whole thing is C++ compiled to WebAssembly, running below in your browser.


Live demo

Click the view first so it takes keyboard focus. It downloads about 6 MB and then spends a few seconds projecting the environment map before the first frame appears.

What the projection actually does

An environment map is a function over directions: give it a direction on the sphere and it gives you back a colour. Spherical harmonics are a set of basis functions over that same sphere, the way sines and cosines are a basis over an interval. Projecting means taking the integral of the environment against each basis function to get one coefficient per basis, and reconstruction is the weighted sum of the bases back again.

The bases come in bands. Band 0 is a single constant, the average colour of the whole environment. Band 1 adds three linear terms that encode which direction the light is coming from. Band 2 adds five quadratic terms, band 3 adds seven. Bands 0 through l give (l+1)² coefficients, so the slider tops out at 16 per channel. That is 48 floats for a whole sky.

Move the l slider from 3 down to 0 and you can watch the reconstruction collapse. At l = 3 you get a blurry but recognisable horizon with the sun roughly in the right place. At l = 1 it is a soft gradient that still points the right way. At l = 0 the entire sky is one flat colour. Nothing here is trying to be a sharp image, which is the point: this representation is for diffuse lighting, where the surface response is so broad that the high frequencies would be integrated away anyway.

Two ways to integrate the same sphere

The integral has to be discretised, and the demo does it twice so you can compare.

The equirect version walks the source image pixel by pixel. That is convenient because the data is already in that layout, but an equirect image massively oversamples the poles, where the rows squeeze into a point. The fix is the sin(θ) term in the solid angle weight, which shrinks each row's contribution as it approaches a pole.

The cube version resamples the environment onto six 128×128 faces first and integrates those. Cube faces have the opposite problem: the corner texels cover more of the sphere than the centre ones, because a flat square projected onto a sphere stretches at its edges. That is what TexelCoordSolidAngle corrects, computing the exact solid angle each texel subtends from the four corners of its footprint.

Both are approximating the same integral, so both should land in roughly the same place. Cycling between them with Space is a decent sanity check on the weights: if either set of solid angles were wrong, the two reconstructions would disagree, usually with the equirect one biased toward whatever colour sits at the poles.

Windowing, and why the reconstruction can go negative

Truncating a series at band 3 is multiplying it by a box: everything up to l is kept at full strength and everything past it is dropped. Sharp cutoffs in one domain turn into ringing in the other, the same Gibbs phenomenon you get truncating a Fourier series at a step edge. In an environment map that shows up as dark haloes around bright light sources, and the reconstruction can dip below zero, which is a negative amount of light.

The window slider softens the cutoff instead. Each band gets scaled by (sin(πl/w) / (πl/w))⁴, a sinc raised to the fourth power, which rolls the higher bands off gradually rather than clipping them. Drag the window down toward 3 and the reconstruction visibly loses contrast as band 3 gets crushed; push it toward 10 and it approaches the unwindowed truncation with the ringing back. The per-band gains are printed under the sliders, and they turn orange once the window is tight enough to zero out a band you asked to keep.

Getting it into the browser

The desktop build gets raylib from vcpkg, which has no Emscripten triplet, so the web branch of the CMake file fetches raylib 5.5 from source and builds it with PLATFORM=Web. On that platform raylib swaps GLFW for Emscripten's own HTML5 input layer and targets GLES2, which maps onto WebGL.

Two things needed changing in the C++ itself. The main loop cannot be a while loop, because the browser owns the frame clock, so the body moved into its own function handed to emscripten_set_main_loop and everything it touched between frames moved to file scope. Clang also rejected the table of basis constants that MSVC had accepted: sqrtf(x) * 0.5 is a double, and narrowing a non-constant double into a float array in braces is an error rather than a warning. The literals needed f suffixes.

The EXR is preloaded into Emscripten's virtual filesystem with --preload-file so LoadEXR finds it at the path it already expected. That is the 5.7 MB the page downloads before anything appears. The 4k source that the desktop build uses is far too heavy for this, both to ship and to project on a single thread, so the web build ships the 1k version. Projection still blocks for a few seconds, and since it happens before InitWindow there is no window to draw a progress bar into. The loading overlay lives in the Emscripten shell page instead and hides itself when raylib logs that the graphics device is up.
